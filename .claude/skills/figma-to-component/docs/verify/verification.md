# 수용기준 & 검증 — Phase 1에서 적고 Phase 3에서 실행한다

> 로드 시점: **Phase 1 끝(Gate 2 직전)** — 수용기준 작성. **Phase 3** — 실행.
> 컨벤션 체크리스트는 [build/review.md](../build/review.md).

**이 문서의 한 줄 요약: "됐다"의 조건을 Phase 1에서 못박고, Phase 3은 그걸 기계적으로 확인만 한다.**

---

## 1. 왜 수용기준을 Phase 1에서 적나

Phase 1은 마스터·Doc을 추출하며 **"이 컴포넌트가 어떻게 동작해야 하는가"를 이미 전부 알아낸다.** 그런데 그걸 적지 않고 넘기면, Phase 3의 체크리스트는 일반론("모양 일치", "폭 반응형")밖에 없어 **컴포넌트별 실제 규칙과 연결이 끊긴다.**

실측 실패: `Order_Voucher` 런에서 Phase 1이 도출한 규칙(disabled=헤더만 · 마스크 start/ing/end · 정렬 center↔flex-start · 아이템 폭 균일 · 플레이스홀더 정원)은 **어디에도 기록되지 않았고**, Phase 3에서 즉흥으로 재구성해야 했다. 하나라도 빠뜨렸으면 조용히 통과했을 것이다.

> 개발 워크플로우의 요구 확정(수용/성공기준) + 단위 루프의 "성공기준 확정(Goal-driven)"에 대응한다. f2c에는 이 단계가 없었다.

## 2. 수용기준의 요건 — **측정 가능해야 한다**

> 🚫 "Figma와 비슷해 보인다" 는 수용기준이 아니다.
> ✅ "`.placeholder`가 정사각이고 `border-radius`가 높이의 절반이다" 는 수용기준이다.

각 기준은 아래 셋을 갖춘다:

| 요소 | 예 |
|---|---|
| **대상** | 셀렉터 또는 스토리 |
| **단언** | 측정값에 대한 참/거짓 명제 |
| **출처** | Figma 실측 / Doc 문구 / 게이트 확정값 중 무엇에서 나왔나 |

```markdown
| # | 대상 | 단언 | 출처 |
|---|---|---|---|
| 1 | `.sec-title .title` (disabled) | color === textDisabled | Doc variant 62034-61850 |
| 2 | `.info .label` (disabled) | color === textPrimary (**dim 아님**) | composition 3-7-1 ⓔ |
| 3 | `.placeholder` | width === height && radius === width/2 | 마스터 실측 64×64 |
| 4 | `.voucher-carousel` (아이템 다수, scrollLeft=0) | class contains `is-mask-right` | Doc `carousel start` |
```

**Phase 1에서 뽑은 행동규칙 1건 = 수용기준 1행**이 원칙이다. 규칙을 도출했는데 기준이 없으면 그 규칙은 검증되지 않는다.

## 3. Phase 3 실행 — 측정이 주(主), 육안이 보조

### ⚠️ 육안 대조는 실측에서 반복적으로 틀렸다

`Order_Voucher` 런의 실제 오판 기록 — **모두 스크린샷을 Figma와 눈으로 비교하다 생긴 것이고, 모두 DOM 측정으로 뒤집혔다**:

| 오판 | 실제 | 왜 틀렸나 |
|---|---|---|
| "disabled면 아이템도 dim된다" | 헤더만 | disabled variant가 **다른 사진 에셋**을 써서 뿌옇게 보임 |
| "이미지가 스트립을 안 채운다" | 정상 (192×64 cover) | 1440×1440을 192×64로 크롭한 **가로 띠**를 아티팩트로 오인 |
| "아이템이 3개만 렌더된다" | 12개 정상 (오버플로우) | 355px 뷰포트에 3개만 보이는 게 **정답** |
| "썸네일이 깨졌다" | 정상 로드 | 흰 배경 제품 사진의 중앙 크롭이 **깨진 아이콘처럼 보임** |

**4전 4패다.** 반면 `getBoundingClientRect`/`getComputedStyle` 측정은 같은 항목에서 **한 번도 틀리지 않았다.**

> 이 스킬은 과거 Chrome MCP 시각 자동화를 *"'일치'라고 거짓 통과한 사례"* 때문에 제외했다. **그 판단의 교훈은 "자동화 금지"가 아니라 "이미지끼리 비교하지 말라"였다.** 이미지 대조는 AI든 사람이든 오판하고, 오판이 "일치"로 굳는다. **측정 단언은 참/거짓이 결정적이라 거짓 통과가 구조적으로 어렵다.** 측정을 주로 올리고 육안은 보조로 내린다.

### 검증 모드 — 측정(기본) / 직접 확인(선택)

측정 검증은 가장 확실하지만 **오래 걸린다**(수용기준 수십 개 × 브라우저 조작). 사용자가 Storybook을 직접 보는 편이 빠를 때가 있으므로 **모드를 사용자가 고른다.**

| 모드 | 하는 일 | 결과 표기 |
|---|---|---|
| **측정** (기본·권장) | Playwright/Chrome으로 수용기준을 하나씩 값으로 단언 — 아래 3-0부터 | 기준별 측정값·판정 표. 전부 통과해야 "통과" |
| **직접 확인** | 측정을 하지 않고, 수용기준을 **스토리별 확인 체크리스트**로 만들어 넘긴다(아래 형식) | **"측정 미실행 — 사용자 확인 모드"**. "통과"라고 쓰지 않는다 |

**언제 정하나** — 우선순위대로:
1. **이미 정해져 있으면 묻지 않는다** — 호출 인자 `--verify=measure|manual`, 또는 사용자가 앞서 "측정은 생략·스토리북으로 볼게" 등을 말한 경우.
2. 아니면 **Phase 3 진입 시 Storybook 요청과 같은 메시지에서** `AskUserQuestion` 1문항으로 묻는다 — 어차피 사용자 응답을 기다리는 지점이라 추가 왕복이 없다. 첫 옵션은 **측정(권장)** 이고, 옵션 설명에 **수용기준 개수**를 적어 소요를 가늠하게 한다.
   - 무응답·타임아웃은 선택이 아니다(전역 규칙) — 추천값인 측정으로도, 직접 확인으로도 간주하지 않는다. 돌아오면 다시 묻는다.
3. 정적 검사·컨벤션 리뷰는 **모드와 무관하게 항상** 수행한다.

**직접 확인 모드의 체크리스트 형식** — 수용기준 1행 = 체크 1줄. 사람이 Storybook에서 바로 볼 수 있게 **어느 스토리에서 무엇을 보면 되는지**까지 적는다:

```
□ [Disabled] 헤더 타이틀·서브만 흐려지고 아이템 라벨은 그대로인가  — 기준 #3 (color: textDisabled 범위)
□ [LongText] 세 줄 모두 말줄임(…)이 걸리는가                        — 기준 #7
□ [ItemMany] 스크롤 끝에서 오른쪽 여백 16px이 남는가                  — 기준 #11 (DevTools 권장)
```

- 육안으로 판별하기 어려운 항목(색 값·px 치수)은 **"DevTools로 확인"**을 붙이거나, 그 항목만 측정하자고 제안한다(부분 측정).
- 체크리스트를 넘긴 뒤 사용자가 실패를 알려주면 **회귀 규칙은 그대로 적용된다**(전역 규칙 "실패는 회귀한다").

### 실행 방법 (측정 모드)

#### 3-0. 도구 환경 준비 (측정 검증 선행조건)

> **측정 검증은 브라우저 자동화 도구 없이는 수행할 수 없다.** 사용자가 직접 확인 모드를 **고르지 않았는데** 도구 미연결을 이유로 "수동 확인 부탁"으로 넘기면 규칙 위반이다 — 연결을 먼저 유도한다(아래 2번).

0. **Storybook은 사용자가 띄운다 (먼저 요청)** — 에이전트가 Bash로 띄운 서버는 샌드박스 안에 갇혀 `curl`은 200이어도 브라우저(Playwright·Chrome)에서는 `ERR_CONNECTION_REFUSED`가 난다(실측). 샌드박스 밖 실행은 권한 분류기가 거부하므로 **우회하지 않는다.** Phase 3에 들어서면 먼저 6006 LISTEN을 확인하고, 없으면 바로 요청한다:
   ```
   측정 검증을 위해 Storybook이 필요합니다. 아래 명령으로 띄워 주세요.
   ! yarn storybook --no-open
   (node 엔진 제약에 걸리면: ! PATH="$HOME/.nvm/versions/node/v18.<x>/bin:$PATH" yarn storybook --no-open)
   ```
   사용자가 띄운 프로세스는 **종료하지 않는다**(사용자 소유).

1. **사용 가능한 도구 탐색** — 아래 우선순위로 확인한다:
   - Playwright MCP (`mcp__playwright__*` 또는 플러그인 제공 `mcp__plugin_fe-mobile_playwright__*` 도구 존재 여부)
   - Chrome MCP (`mcp__claude-in-chrome__*`)
   - `open` + `curl` 폴백 (DOM 측정 불가 → 불합격)

2. **도구가 없으면 연결을 유도한다** — 사용자에게 명시적으로 안내:
   ```
   측정 검증을 수행하려면 브라우저 자동화 도구가 필요합니다.
   Playwright MCP가 도구 목록에 뜨지 않습니다.

   Playwright MCP는 이 레포 .mcp.json에 등록돼 있습니다. /mcp에서 playwright가 실패로 보이면
   nvm에 Node.js 20 이상이 있는지 확인해 주세요(없으면 `nvm install 22` 후 세션 재시작).
   Claude in Chrome을 연결해도 됩니다.

   연결 후 다시 검증을 실행하겠습니다.
   ```

3. **스토리북이 새 컴포넌트를 인식하는지 확인** — 포트(기본 6006) LISTEN 여부(`lsof -i :6006 | grep LISTEN`)와 새 스토리 노출을 본다. **인식하지 못하면 사용자에게 재시작을 요청한다**(0번과 같은 이유로 에이전트가 직접 띄우지 않는다).

4. **도구 연결이 불가능한 경우** — 마지막 수단으로만:
   - 검증을 **"도구 미연결로 측정 미완"** 으로 명시 기록
   - 보고에 미완 사유와 함께 **수동 검증 체크리스트**를 제시
   - 이 경우 Phase 3을 **"조건부 통과"** 로 보고 (완전 통과가 아님)
   - **"도구 없이 육안으로 통과"는 허용하지 않는다** — 실패사례 3번 참조

Storybook을 띄우고(→ SKILL.md Phase 3) 브라우저 자동화로 수용기준 표를 **하나씩 단언**한다. 도구는 무엇이든 좋다(Playwright·Chrome MCP). 핵심은 **"눈으로 비교"가 아니라 "값을 읽어 비교"**라는 것.

```js
// 예: disabled 범위 — 헤더만 dim, 아이템 풀컬러
() => {
  const color = (s) => getComputedStyle(document.querySelector(s)).color;
  return {
    헤더타이틀: color('.sec-title .title'),   // 기대: rgba(0, 0, 0, 0.2)
    아이템라벨: color('.info .label'),        // 기대: rgb(0, 0, 0)  ← dim 아님
  };
}
```

**측정으로 잡히는 것** (육안으론 못 잡거나 오판함):
- 색 토큰 적용 범위 (disabled/pressed가 **정확히 어디까지**)
- 폭 균일성 (`items.map(i => i.getBoundingClientRect().width)`)
- 말줄임 실제 발동 (`scrollWidth > clientWidth`)
- 원/알약 판별 (`width === height` && `radius`)
- 마스크 상태 전이 (scrollLeft 조작 → class/`maskImage`)
- 이미지 로드 성공 (`complete`·`naturalWidth`·에러 UI 부재) ← **크롭된 사진을 "깨졌다"고 오판하는 걸 막는다**

**여전히 육안이 필요한 것** (측정으로 환원 안 됨):
- 크롭 위치가 의미 있는가 (사진의 중요 부분이 잘렸나)
- 전반적 시각 균형·간격이 어색하지 않은가
- Figma 임베드(`design`에 nodeId 연결 시 Design 패널)와의 최종 인상 대조

### 스토리 샘플 데이터도 검증 대상이다

**64px 썸네일에서 사진으로 읽히지 않는 샘플 이미지는 육안 검증을 무력화한다.** 실측: `cdn-dev` 샘플이 흰 배경 제품 사진이라 중앙 크롭이 깨진 아이콘처럼 보였고, **같은 오판을 3회 반복**했다. 리뷰어도 똑같이 오판한다. 샘플은 **그 크기에서 사진으로 읽히는 것**으로 고른다.

### 스토리 검증 (공통 UI 필수 — 측정 모드)

스토리도 산출물이다. 컴포넌트 수치가 맞아도 **목록이 섞였거나 다른 variant에 연결됐거나 래퍼가 디자인에 없는 모양을 덧대면** 대조가 틀어진다(실측: FE-6555에서 셋 다 발생). 측정 모드에서 함께 확인하고 결과 보고에 포함한다(산출물 확장이 켜져 있으면 `02_verification.md`에도 남긴다):

| 항목 | 방법 | 기대 |
|---|---|---|
| **목록·순서** | 매니저 사이드바 DOM(`[data-item-id^="{title-id}--"]`)의 텍스트를 순서대로 뽑는다 | 설계 노트 「스토리 구성」 표와 1:1 일치 |
| **variant 연결** | 각 스토리 iframe에서 `__STORYBOOK_PREVIEW__.currentRender.story.parameters.design`의 `node-id` | 매트릭스 스토리 = 해당 variant nodeId(`get_metadata`와 대조), Figma 밖 = 세트 nodeId |
| **래퍼 구조** | 컴포넌트 루트와 부모들의 computed style | 컴포넌트 `outline: none`(스타일 미접촉) · 경계 컨테이너 border가 컴포넌트에 사방 1px 밀착 · 캔버스 배경·여백만 존재(Figma에 없는 흰 박스·radius 없음) |
| **전 스토리 렌더** | 스토리마다 `/iframe.html?id=…&viewMode=story`를 iframe으로 열어 루트 존재·가로 넘침(`scrollWidth > clientWidth`) 확인 | 전부 렌더 · 넘침 없음 · 콘솔에 스토리 기인 에러 없음 |

- 순서 근거: `storySort`에 `includeNames`가 없어 **export 순서 = 사이드바 순서**다. 순서가 다르면 export 순서를 고친다.
- iframe을 여러 개 띄우면 매니저 콘솔에 `received … but was unable to determine the source` 에러가 찍힌다 — 측정 부산물이므로 스토리 에러로 세지 않는다.

## 4. 정적 검사와의 관계

정적 검사(type-check·lint·stylelint)는 **수용기준을 하나도 검증하지 못한다.** 위 표의 모든 항목이 정적 검사를 통과한 채로 틀릴 수 있다. 순서는:

1. **정적 검사** — 문법·타입·컨벤션 (→ SKILL.md Phase 3)
2. **컨벤션 리뷰** — 별도 컨텍스트 (→ [build/review.md](../build/review.md))
3. **측정 검증** — 수용기준 표 실행 ← **여기가 실제 정합을 보증한다**
4. **육안** — 측정으로 환원 안 되는 것만

결과는 기준별 측정값과 판정 표로 보고한다.

**기준 중 하나라도 실패하면 통과가 아니다.** 원인에 따라 회귀한다 → SKILL.md "실패 회귀".
