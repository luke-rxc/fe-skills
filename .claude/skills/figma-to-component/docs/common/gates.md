# 게이트 — 카탈로그 · 무응답 규칙 · 카드 규약 · 실패사례 아카이브

> 로드 시점: 전 Phase 참조. **방어 규칙의 단일 원본**이다 — SKILL.md와 다른 docs는 여기를 링크만 하고 규칙을 재정의하지 않는다.

## 설계 원칙 — 질문은 언제 존재하나

> **질문의 존재 근거는 "스킬이 그 값을 알 수 없다"여야 한다.**
> **"스킬이 틀릴 수 있다"는 질문의 근거가 아니다** — 그건 근거 표기 + 반증 가능한 선택지로 처리한다.

이 기준으로 갈린 결과:

| | 항목 | 이유 |
|---|---|---|
| **삭제** | 파일 타입 | URL fileKey 역조회는 결정적 함수 |
| | 서브 세트 id | 섹션 URL이면 probe 트리로 정확히 도출(마스터 URL이면 존재만 감지되고 id는 못 얻으므로 URL을 **요청**한다 — 판단이 아니라 입력 요청) |
| | Doc(감지 시) | 이름 규칙으로 감지됨 |
| | componentGroup(섹션 감지 시) | PDS **섹션 이름**이 곧 그룹명이다 — probe 트리의 `<section name>`에서 읽힌다(→ [plan/intake.md](../plan/intake.md) §6-3) |
| **존치** | **랜딩** | Figma에 정보 자체가 없다 — 어떤 probe로도 못 얻는다 |
| | **category** | 코드베이스 taxonomy(`src/stories/menu.ts`). Figma 어디에도 없다 |
| | componentGroup(섹션 미감지 시) | 마스터 URL이면 `get_metadata`가 자식만 보여줘 부모 섹션이 안 보인다 — Q3 category와 **한 문항**으로 묻는다 |
| | **네이밍** | PascalCase화는 도출 가능하나 variant/약어 제거·충돌 회피는 규범적 판단 |
| | features/apps · 이름 | 비즈니스면 **도메인 횡단(`src/features/{featureName}`)인지 도메인 전용(`src/apps/{domain}`)인지**, 그리고 그 이름이 뭔지 Figma에 없다 |
| | 재사용/확장/신규 | 의사결정이지 사실이 아니다 |

## 🚨 전역 규칙 — 무응답·타임아웃은 확정이 아니다

**보존해야 할 불변식:**

> **확정값은 그 값을 묻는 선택지에 대한 사용자의 명시적 선택 결과여야 한다 — 질문 횟수와 무관.**

- `AskUserQuestion`이 *"No response after Ns / 사용자가 자리를 비움"* 으로 응답 없이 반환돼도 **첫 옵션(추천값)을 자동 확정으로 간주하면 규칙 위반**이다. 타임아웃은 "아직 답을 못 받은 상태"일 뿐이다.
- **배칭 호출이 통째로 타임아웃** → 그 호출의 **모든 문항이 미확정**. **부분 응답** → **응답된 문항만 확정**.
- 미확정 값에 의존하는 후속 단계(추출·생성 등)로 **진행하지 않는다.** 사용자가 돌아오면 **같은 질문을 다시 던진다.**
- 부득이하게 잠정값으로 작업을 미리 해 뒀다면 **"확정이 아니라 무응답 시 잠정 진행한 것"이라고 명시**하고 확정을 다시 받는다. **확정 전에는 "완료"로 보고하지 않는다.**
- 오직 사용자가 **명시적으로 위임한 문구**(예: "네가 알아서 이름 정해"를 답으로 실제 선택/입력)만 위임이다 — 위임조차 추천값 자동 수락이 아니라, 추천값을 제시해 **명시적 확정**을 받아야 한다. **무응답은 위임이 아니다.**

## 배칭 — 왜 안전한가

`AskUserQuestion`은 한 호출에 **최대 4문항**을 담고 **문항별로 개별 답을 돌려준다.** 즉 4문항 배칭 = **상호작용 1회 + 확정 4개**다.

실패사례가 막으려던 건 "질문이 적은 것"이 아니라 **"스킬이 값을 정하고 조용히 넘어간 것"**이다(아카이브 참조). 배칭은 그 중 어느 것도 하지 않는다.

**따름정리**: **열린 게이트에 질문 1개를 더하는 비용은 0이다.** 애매한 값은 스킵하지 말고 옵션에 pre-fill해서 확정받는다.

### 4문항 초과 시 분할 — 우선순위 = blast radius

그 답이 뒤집히면 **몇 개가 무효가 되나**로 정렬한다.

- **Gate 1**: 마스터(뒤집히면 전부 무효) > 기존 충돌 3-way(ⓐ면 생성 자체가 없음) > 경로/도메인(정책 분기) > 서브 URL · Doc(추출 대상)
- **Gate 2**: 랜딩 > 네이밍 > category > 서브 분리 > 시맨틱 역할 > 정책문서

초과분은 **Gate 1b로 분할(2회)** 한다 — 중요한 걸 빼고 4개에 우겨넣는 것보다 낫다.

## 카드 규약 — rubber-stamp 완화

배칭이 실제로 위험한 지점은 **질문이 아니라 카드**다. 카드에 사실을 늘어놓고 사용자가 4문항만 답하면 **카드의 나머지 줄은 암묵 승인**된다. 4가지로 완화한다.

1. **기계적 경계선** — 카드에 오를 자격 = **ⓐ 도구 응답 원문 인용** 또는 **ⓑ 리포지토리 file:line 인용**이 가능한 것. 근거를 못 다는 항목은 **자동으로 질문**이 된다.
   - 파일타입 = `types.ts:10` 역조회 ✓ → 카드
   - 랜딩 = 근거 없음 → 질문
   - ⚠️ **서브에이전트(Explore) 보고는 ⓑ가 아니다.** Explore가 file:line을 인용해도 그건 "그 파일이 존재한다"는 근거지 **"그게 이 Figma 요소에 맞다"는 근거가 아니다.** 재사용 매핑 행은 **Figma 실측 ↔ 대상 CSS 대조**를 마쳐야 ⓑ가 된다(→ [plan/extraction.md](../plan/extraction.md) §4). 실측 실패: `ButtonBubble size="small"`·`TitleSub` 추천을 그대로 카드에 올려 **2건 모두 오답**이었다.
2. **강제 독해 (핵심)** — 카드를 "읽고 넘기는 요약"이 아니라 **질문의 선택지 자체**로 만든다. 마스터 후보가 곧 옵션이면 카드를 안 읽고는 답할 수 없다. 후보가 1개여도 2지선다로 낸다(비용 0).
3. **출처 라벨** — 카드/옵션 각 줄에 `[자동 도출]` / `[추천]` / `[사용자 제공]` / `[호출측 확정]`. 사용자가 **어디를 검증해야 하는지** 알 수 있게. **라벨 없는 값은 카드에 못 올린다.**
4. **"없음" 결론에 대한 명시 확인** — 아래 Gate 2 Q1 참조.

확정 카드([plan/intake.md](../plan/intake.md) §8)를 제시하고 `AskUserQuestion` **1회**(≤4문항). 조건부 문항은 해당할 때만.

| # | 문항 | 조건 |
|---|---|---|
| 1 | **마스터** — 후보 2+ → 선택 / 1개 → 확인 / 0개 → 재입력·비즈니스 전환 | 항상 |
| 2 | **경로** — pui / features / apps 3지선다 (+ features·apps면 그 이름) | `fileKey≠pds` 또는 F.M.C. 아님 또는 원칙 2~4 후보 |
| 3 | **Doc 유무** | 서브트리 내 미감지 |
| 3-2 | **서브 컴포넌트 URL** — 감지된 서브 이름을 나열하고 URL을 받는다(Other). 옵션: 섹션 URL로 다시 주기 · 서브는 분리하지 않고 루트에 포함 | 마스터 URL 직접 + 인스턴스 신호 있음 + **Doc·섹션으로도 서브 id를 못 얻음**(→ [plan/intake.md](../plan/intake.md) §6-2) |
| 4 | **기존 충돌 3-way** | grep 히트 |

### Q2 — 경로는 2지선다가 아니라 3지선다다

**UI가 들어갈 수 있는 곳은 셋이다** — `src/pui/` · `src/features/{featureName}/components/`(도메인 횡단 재사용) · `src/apps/{domain}/components/`(도메인 전용). 실측: `features/*/components` 17곳에 UI 파일 108개가 산다. **비즈니스를 `apps`로만 단정하지 말 것.**

- **원칙 2~4 후보면 어느 원칙인지와 "팀 합의 필수" 경고를 선택지에 함께 적는다.** "여러 도메인에서 쓰인다"는 근거가 아니다. 비즈니스 로직·데이터 연동을 품으면 **features**가 정답 → [build/business-policy.md](../build/business-policy.md) 0번.
- `{featureName}`/`{domain}` **이름도 같은 문항에서 받는다**(Other 자유입력). 경로만 정하고 이름을 미확정으로 두면 생성 시 또 물어야 한다.

### Q4 — 기존 구현 충돌 3-way

마스터 nodeId가 기존 `*.stories.tsx`의 `design`에 이미 박혀 있으면 신규가 아닐 수 있다. **"기존이 있으니 무조건 재사용"으로 단정하지 않는다** — 재사용/확장/신규는 **사용자 판단**이다.

- ⓐ **기존 재사용/확장** — 그대로 쓰거나 variant/prop만 확장(신규 생성 없음)
- ⓑ **기존 기반 리디자인·통합** — 기존을 1:1 베이스로 통합/개편
- ⓒ **아예 신규 개발** — 별도 이름으로 전면 새로 작성. 선택 시 Gate 2 네이밍에서 **충돌 회피 이름**으로 확정

> **스캐폴딩 이행기 — 같은 이름의 평평한 기존 컴포넌트.** 기존이 `src/pui/{name}/`(이행 전)에 있고 새 스캐폴딩(`src/pui/{category}/{name}/`)에 ⓑ·ⓒ로 새로 만들면, **폴더는 달라도 컴포넌트명·export명·스토리 이름이 겹친다**(실측: `OrderVoucher` 재생성 시 스토리 이름 충돌 → 임시로 `OrderVoucherNew`를 붙임). 이름을 생성 중에 임시로 짓지 말고 **Gate 2 네이밍에서 함께 확정**한다 → Q2 "이행기 이름 충돌".

기존 구현이 작업 트리에서 **삭제(staged) 상태여도** `git show HEAD:<path>`로 원본을 읽어 베이스로 참고한다. **여러 기존 컴포넌트가 하나의 마스터(size/상태 variant)로 합쳐지는 케이스**면 PDS가 다수 컴포넌트보다 **variant 통합을 선호**함을 환기하되, 방향은 사용자에게 확정받는다.

### Q1 — 랜딩: 신호 유무로 질문 형태를 바꾼다

#### "랜딩"의 정의

> **"랜딩"이란 컴포넌트 내부에서 어떤 영역들이 탭/클릭 시 이동(링크) 기능을 가져야 하는지를 뜻한다.**
>
> - 컴포넌트가 화면에 배치되는 위치(URL/라우트/페이지)가 **아니다.**
> - 도메인 라우팅(URL)은 pui가 아닌 `apps/`·`features/`에서 결정하므로, 여기서 묻지 않는다.
> - **컴포넌트 내부의 인터랙션 가능한 터치 포인트(탭 → 이동)**를 확정하는 것이다.
> - 예: "사용 버튼 탭 → 바우처 사용 플로우로 이동", "각 아이템 탭 → 해당 바우처 상세로 이동"
> - 확정된 랜딩 영역은 Props 설계 시 `onPress`, `link`, `onClick` 등의 핸들러/prop으로 반영한다.

**Figma엔 랜딩(네비게이션) 정보가 없다.** 마스터 구조 + Doc 인터랙션 신호 + 스크린샷으로 **추론해 표로 제시**하고 사용자가 확정/수정한다.

> ⚠️ **"디자인에 미명시" ≠ "랜딩 없음"(핵심).** press 오버레이·화살표·👆🏼 같은 신호가 **하나도 없어도** 실제로는 랜딩이 필요한 카드/아이템이 많다(디자인 가이드는 보통 press·네비게이션을 정의하지 않는다). **신호 부재를 근거로 "표시 전용"이라 결론내지 말 것.**

그래서 **질문 형태를 신호 유무로 바꾼다** — 같은 1문항이지만 "랜딩 없음"이 **사용자의 답으로만** 성립하게:

| 신호 | 질문 |
|---|---|
| **있음** | "이 랜딩 표대로 진행할까요?" (표대로 / 수정(Other)) |
| **0건** | **"이 컴포넌트에 랜딩(클릭 이동)이 필요한가요?"** (필요 / 불필요 / 일부만) |

추론 휴리스틱:
- 콘텐츠 카드/리스트 아이템류 → **카드 전체가 앵커**(`Action is="a"`) 후보
- 명확한 버튼(추가·팔로우·북마크·더보기) → **`button`**(`Action` + onClick) 후보, 전체 앵커 **밖** 별도 배치
- 텍스트·배지·구분선 등 단순 표시 → 랜딩 아님 **(단, 위 ⚠️대로 불확실하면 재확인)**
- Doc의 👆🏼/화살표/Pressed 오버레이 → 클릭 가능 영역의 근거

**한 컴포넌트에 랜딩은 여러 개일 수 있다.** 영역별 N행 표로:

| 영역 | 랜딩? | 요소 | 링크 소스 | 비고 |
|------|------|------|----------|------|
| 카드 전체 | ✅ | `Action is="a"` | `link` 오버라이드 + `getLink` 폴백 | `aria-label` |
| 썸네일(라이브중) | ✅ | `Action is="a"` | `getLink(LIVE,{liveId})` | 상태별(onAir) 분기 |
| 팔로우 버튼 | ✅ | `Action`(button) | onClick | 전체 앵커 밖 별도, `aria-pressed` |
| 주소 텍스트 | ❌ | — | — | 표시 전용 |

- **중첩 금지(핵심)**: `<a>` 안에 또 다른 `<a>`/`<button>`을 넣을 수 없다. 전체+내부 랜딩이 공존하면 **영역별로 분리**한다. 코드화는 → [build/guide/composition.md](../build/guide/composition.md) 3-4.

### Q2 — 네이밍

**위임해도 생략하지 않는다.** "너가 알아서"는 추천값 자동 수락이 아니다 — 추천명을 첫 옵션으로 제시해 **명시적 확정**을 받는다. 파일/폴더/export/스토리명이 이름에 종속되므로, 미확정 이름으로 파일을 만들면 전체를 리네임해야 한다.

- **추천 규칙**: Figma 마스터 노드명(variant/상태/약어 토큰 제거)을 **PascalCase**로 → 컴포넌트명. 폴더는 그 **camelCase**(`Address` → 폴더 `address`, 파일 `Address.tsx`).
- **충돌 점검**: 추천 폴더명이 대상 경로에 **이미 있거나 작업 트리에서 삭제(staged)된 경로면 경고**하고 다른 이름을 제안한다(기존 덮어쓰기 금지). 삭제 staged 경로를 재생성하면 사용자의 진행 중인 작업과 섞인다.
- **제시 형태**: 최종 생성 경로까지 — 예 `src/pui/dataDisplay/address/components/Address.tsx`(공통 UI는 카테고리 폴더 포함).
- **이행기 이름 충돌** — Q4에서 같은 이름의 평평한 기존 컴포넌트를 두고 ⓑ·ⓒ를 골랐으면, 폴더가 달라도 **컴포넌트명·export명·스토리 이름**(`defineMeta`의 `componentGroup`·스토리 title)이 겹친다. 옵션을 함께 제시해 확정받는다:
  - ⓐ **같은 이름 유지** — 새 컴포넌트가 정식 이름을 갖고, 기존은 이행 대상으로 남긴다(스토리 `componentGroup`만 구분 — 예: 기존 쪽을 그대로 두고 새 쪽 그룹명을 확정).
  - ⓑ **임시 접미사** — `…New` 등으로 구분하고, 기존 정리 시 리네임한다(리네임 대상을 보고에 남긴다).
  - 생성 중에 스킬이 임의로 접미사를 붙이지 않는다 — 파일·export·스토리 전부가 이름에 종속된다.
- `componentGroup`은 네이밍이 아니라 **PDS 섹션 이름**이다 → Q3.

### Q3 — category

⚠️ **Figma node-id/metadata/design_context 어디에도 Storybook 메뉴 분류가 없다.** **형제 컴포넌트 값을 미러링해 조용히 확정하지 말 것** — 형제 값은 추천 힌트일 뿐 정답 기준이 아니다.

1. **옵션 목록을 `src/stories/menu.ts`에서 읽어** 실제 `StoriesMenu.PDS.*` 키를 확인한다(런타임 값이 단일 기준 — `System`/`Button`/`Navigation`/`DataEntry`/`DataDisplay`/`DataDisplayCardType`/`Feedback`).
2. **컴포넌트 성격으로 추천값을 고른다** — 값을 선택·입력받는 인터랙션 컴포넌트(선택 카드·토글·스텝퍼) → `DataEntry`, 순수 표시 카드 → `DataDisplay(CardType)`. 형제 category는 **참고만** 하고 성격이 다르면 따르지 않는다.
3. 추천값을 첫 옵션(`(Recommended)`)으로, 나머지 후보를 옵션으로, "직접 입력"은 Other로.
4. **category가 곧 배치 폴더다** — 카테고리 폴더와 1:1(→ 컨벤션 「배치」). 각 옵션에 최종 경로를 함께 적는다(예 `DataDisplay` → `src/pui/dataDisplay/brandProfile/`). Non-PDS(원칙 2~4)는 `NonPDS` → `nonPds/`.

#### componentGroup — PDS 섹션 이름

스토리 title은 `category/componentGroup/name`이다(`src/pui/_utils/meta.ts` `buildTitle`). **`componentGroup`은 컴포넌트명이 아니라 그 컴포넌트가 놓인 PDS 섹션 이름**이다 — 실측: `GoodsSmall`·`GoodsMedium`·`GoodsLarge`·`PriceArea` → `'Goods'`, `BrandCard`·`BrandCardLarge`·`BrandListItemMedium` → `'Brand'`, `TextField` → `'Input & TextArea'`. 컴포넌트명과 같은 건(`Voucher`) 섹션 이름이 우연히 같을 때뿐이다.

| 인테이크 결과 | 처리 |
|---|---|
| **섹션 감지**(섹션 URL, 또는 probe 트리에 `<section>` 조상이 보임) | `<section name>`을 그대로 쓴다. **묻지 않는다** — 카드에 `[자동]`으로 올린다 |
| **섹션 미감지**(마스터·Doc URL) | Q3 category와 **한 문항**으로 묻는다(Gate 2 문항 수는 늘지 않는다). 옵션 = `category / componentGroup` 조합 |

미감지 시 추천값(근거를 함께 적는다):
1. **Doc 제목 텍스트** — Doc이 확정돼 함께 추출했다면 상단 제목(예: `Goods`). Doc 프레임 이름(`Card_Brand Doc`)은 그룹명이 아니므로 쓰지 않는다.
2. **같은 섹션 형제의 기존 값** — Doc·스크린샷에 함께 보이는 형제 마스터가 이미 구현돼 있으면 그 스토리의 `componentGroup`(`grep -rn "componentGroup" src --include='*.stories.tsx'`).
3. 둘 다 없으면 추천 없이 "섹션 이름을 알려주세요"로 묻는다. **컴포넌트명을 기본값으로 채우지 않는다.**

- **Non-PDS(`StoriesMenu.NonPDS`)면 `componentGroup`을 두지 않는다** — title이 `category/name`이다(→ [build/guide/structure.md](../build/guide/structure.md) 4번 「팀 작성 규칙」 4). 묻지 않는다.

⚠️ **이름이 비슷하다고 묶지 않는다** — 근거는 섹션이다(실패사례 #3·#15).
